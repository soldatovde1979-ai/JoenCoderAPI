# Подключение Roo Code к шлюзу OpenCoder (локальный прокси)

Утилита `gw-proxy` — локальный прокси, который принимает OpenAI-совместимые запросы
от Roo Code и подписывает их устройственным ключом OpenCoder. Roo начинает ходить
на те же модели, что и OpenCoder (`pro`, `flash`, 288K контекста, понимают картинки).

```
Roo Code  ──http://127.0.0.1:8787/v1──>  gw-proxy.mjs  ──подписанный HTTPS──>  code.accelstacks.com/gw
```

Есть второй вариант — **без прокси, портов и фоновых процессов**: для Zoo Code
подпись дописывается прямо в расширение (см. «Zoo Code без прокси (патчер)»).

## Файлы (3 шт.)

| Файл | Что делает |
|---|---|
| `gw-proxy.mjs` | Сам прокси (один файл, без зависимостей) |
| `gw-proxy.cmd` | Запускалка: проверяет Node.js и, если его нет, ставит через winget |
| `gw-proxy-wt.cmd` | Тот же запуск, но новой вкладкой в окне Windows Terminal |

Папка с файлами значения не имеет: все пути внутри относительные
(сейчас это `c:\Projects\OpenCoderAPI\ZOO`, но папку можно перемещать).

### Если OpenCoder установлен в другом каталоге

Прокси ищет установку OpenCoder в `C:\OpenCoder` (нужен только файл `cli.js` —
из него считается отпечаток сборки `x-ccw-build`). Другой путь задаётся одной
строкой в `gw-proxy.cmd`:

```bat
rem OpenCoder install folder. Change this single line if OpenCoder is installed elsewhere.
set "OPENCODER_HOME=D:\Tools\OpenCoder"
```

Либо переменной окружения `OPENCODER_HOME` (тогда `gw-proxy.cmd` можно не править).
Фактический путь видно в выводе при старте:

```
     OpenCoder: C:\OpenCoder (cli.js найден)
```

Если файл не найден, прокси напишет предупреждение и продолжит работу
с пустым `x-ccw-build` — шлюз такой запрос принимает, но отпечаток сборки
будет отсутствовать.

Креденшалы (`cc-web-credentials.json`) от каталога установки **не зависят**:
они всегда лежат в `%LOCALAPPDATA%\OpenCoder\` профиля пользователя.

## Настройка (3 шага)

**1. Запустите `gw-proxy.cmd` двойным кликом** (или `node gw-proxy.mjs` из терминала).

Вывод прокси идёт **в окно консоли** и одновременно дублируется в файл
**`gw-proxy.log`** рядом со скриптом — файл ведёт сам прокси. Лог не стирается
при перезапуске: когда он превысит 1 МБ, при следующем старте он
переименовывается в **`gw-proxy.prev.log`** (одно предыдущее поколение), и
запись начинается в новый `gw-proxy.log`. Каждая строка в файле имеет метку
времени вида `[2026-11-03 10:45:35]` и пишется без ANSI-кодов (в окне цвет
сохраняется). Окно запуска можно свернуть. При старте прокси сам проверяет окружение
(результат — в начале `gw-proxy.log`):

```
=== gw-proxy: проверка окружения ===
[OK] Node.js 24.14.1
[OK] Креденшалы OpenCoder найдены (managed device)
[OK] Roo Code установлен                    ← или Zoo Code (форк Roo) — тоже подойдёт
[!!] В Roo нет профилей: OC, OC PRO, OC PRO+ ...
[!!] Автозапуск: не настроен — прокси надо запускать вручную.
```

Если расширения Roo нет — прокси установит его сам (`code --install-extension`).
Если нет входа в OpenCoder — прокси подскажет и завершится: войдите в OpenCoder и запустите снова.

```
=== gw-proxy: запущен ===
     Адрес для Roo / клиентов: http://127.0.0.1:8787/v1
```

Пока работаете с Roo/Zoo — окно запуска держите открытым (можно свернуть);
закрыли окно — прокси умер.

2. В **Roo Code → Settings → API Provider → OpenAI Compatible** создайте профили
   (прокси при старте сам напечатает, каких не хватает):

| Имя профиля | Base URL | API Key | Model |
|---|---|---|---|
| `OC` | `http://127.0.0.1:8787/v1` | `local` | `flash` |
| `OC PRO` | `http://127.0.0.1:8787/v1` | `local` | `pro` |
| `OC PRO+` | `http://127.0.0.1:8787/v1` | `local` | `pro` + Reasoning Effort = High |

3. Выберите профиль в Roo и проверьте соединение.

## Проверка из терминала (без Roo)

```
curl -H "Authorization: Bearer local" http://127.0.0.1:8787/v1/models
```
Ожидается JSON со списком моделей (`pro`, `flash`).

## Запуск в Windows Terminal

Если пользуетесь Windows Terminal, удобнее запускать прокси новой вкладкой уже
открытого окна WT (двойным кликом по `gw-proxy-wt.cmd`):

```
gw-proxy-wt.cmd
```

- Окно WT уже открыто → прокси откроется **новой вкладкой** в нём (заголовок вкладки — `gw-proxy`).
- WT закрыт → откроется новое окно WT с вкладкой прокси.
- Windows Terminal не установлен → скрипт сам запустит обычный `gw-proxy.cmd`.

## Автозапуск

При каждом старте прокси пишет, включён ли автозапуск. Включить:
```
schtasks /create /tn "gw-proxy" /tr "node c:\Projects\OpenCoderAPI\ZOO\gw-proxy.mjs" /sc onlogon /rl limited /f
```
(путь — где лежит ваш `gw-proxy.mjs`). Выключить: `schtasks /delete /tn "gw-proxy" /f`.
Альтернатива — ярлык на `gw-proxy.cmd` (или `gw-proxy-wt.cmd`) в `shell:startup`.

## Отладка (уровень логов)

Уровень задаётся при запуске — аргументом или переменной окружения:

```
gw-proxy.cmd debug=2          :: аргумент
set GW_PROXY_DEBUG=2          :: переменная (действует в этом окне)
gw-proxy.cmd
```

| Уровень | Что попадает в лог |
|---|---|
| `debug=0` | только старт, предупреждение `[долго] шлюз отдал заголовки за N с`, `[warn] не-stream ответ`, `[fatal]` |
| `debug=1` **(по умолчанию)** | + все ошибки: `[err]` (включая тело ответа шлюза при статусе ≥ 400), обрыв стрима и прерванный клиентом ответ |
| `debug=2` | + каждый запрос: `[start]` (приём, с числом параллельных), `[req]` (статус и время ожидания шлюза), `[done]` (итог по факту закрытия ответа) |

Аргумент важнее переменной. Уровень применяется только при старте — «на лету» не меняется.

Записи, которые пишутся независимо от уровня:

| Запись | Что означает |
|---|---|
| `[err] ... тело: ...` | шлюз ответил статусом ≥ 400; в логе — первые 800 символов его тела (причина отказа) |
| `[warn] не-stream ответ` | на запрос со `"stream": true` шлюз ответил 200, но не SSE — в теле JSON (обычно ошибка внутри «успешного» ответа). Тело пишется в лог, клиент получает его как есть |
| `[err] stream: ...` | поток от шлюза оборвался, не доехав до конца |
| `[err] клиент прервал ответ` | клиент (Zoo/Roo) закрыл соединение, не дочитав ответ |
| `[fatal]` | прокси упал или не смог занять порт; след остаётся в логе, процесс завершается |

## Если что-то не работает

| Симптом | Причина и лечение |
|---|---|
| Прокси пишет про отсутствие креденшалов | Не выполнен вход в OpenCoder. Войдите в OpenCoder, запустите прокси снова. |
| Порт 8787 занят (`EADDRINUSE`) | Уже запущен второй экземпляр, либо смените порт: `set GW_PROXY_PORT=8788` перед запуском (и поправьте Base URL в Roo). |
| Ошибка TLS (`unable to verify`, `certificate`) | Выполните `set NODE_EXTRA_CA_CERTS=C:\OpenCoder\ca.pem` в том же окне перед запуском прокси (путь — если OpenCoder стоит не в `C:\OpenCoder`, поправьте). |
| Roo получает 401 `invalid_client_proof` | Токен OpenCoder просрочен — откройте OpenCoder, дождитесь входа, перезапустите прокси. |
| Roo/Zoo зависает на запросе, прокси-процесс жив, но не отвечает даже на `/v1/models` | **Фриз QuickEdit**: случайный клик по окну консоли выделяет текст, и блокирующая запись в консоль навсегда останавливает Node. В Windows Terminal выделение мышью процесс не блокирует; в старом conhost отключите QuickEdit: `reg add HKCU\Console /v QuickEdit /t REG_DWORD /d 0 /f` (для новых окон консоли). |
| Roo/Zoo получает 502 `The operation was aborted` | Шлюз не отдал заголовки за 60 с (`GW_PROXY_TIMEOUT_MS`, можно переопределить перед запуском). Проверьте сеть/статус шлюза и повторите. |
| Кажется, что запрос «завис» | Запустите прокси с `debug=2` (см. раздел «Отладка») — в логе видно каждый запрос: `[start]` (принят), `[req]` (шлюз ответил, сколько ждали) и `[done]`. Строка `[долго] шлюз отдал заголовки за N с` пишется всегда и означает, что медленно отвечает шлюз, а не прокси. Несколько запросов идут **параллельно** — ждать завершения одного, чтобы работал другой, не нужно. |
| Roo зависает на запросе | Проверьте, что прокси-процесс жив (`tasklist \| findstr node`) и Base URL в Roo без опечаток (именно `/v1` на конце). |
| Zoo показывает «Internal server error», а в логе пусто | Смотрите не только `gw-proxy.log`, но и `gw-proxy.prev.log` (там лог предыдущего запуска). Ищите записи `[warn] не-stream ответ`, `[err] ... тело:`, `[err] stream:` — они содержат ответ шлюза и причину. Если записей нет вовсе, ответ до прокси не доходил: проверьте Base URL и что запросы идут именно на порт прокси. |
| Нужно понять, что именно вернул шлюз | Запустите с `debug=2`: при статусе ≥ 400 и при «200 без SSE» тело ответа попадает в лог (`[err] ... тело:` / `[warn] не-stream ответ`). Это и есть текст ошибки от шлюза. |
| Сервис запущен, а нужно прогнать смоук-тест | Останавливать рабочий прокси не нужно: тест поднимает свой экземпляр на порту `18787`, сервис остаётся на `8787`. Смешиваются только записи в общем `gw-proxy.log`. |

## Zoo Code без прокси (патчер)

Zoo Code — открытый форк Roo, и в его бандле есть единственная точка, где создаётся
OpenAI-клиент. Патчер добавляет туда `fetch`, который подписывает **только** запросы
к хосту `code.accelstacks.com`; всё остальное уходит без изменений.

```
Zoo Code (в процессе расширения)  ──подписанный HTTPS──>  code.accelstacks.com/gw
```

| Файл | Что делает |
|---|---|
| `oc-sign.cjs` | Подпись запросов (ed25519-v1). Формат тот же, что в `gw-proxy.mjs` |
| `oc-sign.mjs` | Тонкая ESM-обёртка над `oc-sign.cjs` (для использования из Node) |
| `patch-zoo.mjs` | Патчер: две вставки в `dist/extension.js` + бэкап `.orig` |
| `patch-zoo.cmd` | Запускалка патчера (проверяет наличие Node.js) |

**1. Патч.** Двойной клик по `patch-zoo.cmd` или из терминала:

```
node patch-zoo.mjs --check     :: только отчёт, ничего не меняет
node patch-zoo.mjs             :: применить (повторный запуск безопасен)
node patch-zoo.mjs --revert    :: откат из extension.js.orig
```

Патчер сам находит самую свежую установленную версию расширения, делает резервную
копию `dist\extension.js.orig` (один раз) и проверяет синтаксис результата до записи.
Точка вставки ищется по параметрам конструктора клиента (`baseURL`, `apiKey`,
`defaultHeaders`, `timeout`), а имя класса берётся из найденного кода — поэтому
переименование класса минификатором (например, `Sn` → `Tn` в версии 3.97.100754)
патч не ломает.

Если точка вставки не найдена или таких точек несколько (изменилась версия Zoo),
файл **не** трогается и патчер завершается с кодом 2 — нужен новый паттерн.
Проверить заранее: `node patch-zoo.mjs --check` печатает число найденных точек.

**2. Настройка в Zoo Code → Settings → API Provider → OpenAI Compatible:**

| Поле | Значение |
|---|---|
| Base URL | `https://code.accelstacks.com/gw/v1` |
| API Key | любой непустой (реальная авторизация — устройственным ключом OpenCoder) |
| Model | `pro` или `flash` |

Провайдер должен быть именно **OpenAI Compatible**, не Azure: `fetch` подставляется
в не-Azure ветку клиента.

**3. Перезапуск.** `Ctrl+Shift+P` → `Developer: Reload Window`.

Порядок важен: применяйте патч, когда VS Code **закрыт**. Запись файла может пройти
и на работающем окне, но загруженный в память бандл не обновится — в лучшем случае
патч просто не подействует до перезапуска.

После каждого обновления Zoo Code патч **слетает**: VS Code ставит расширение в новую
папку версии, вставок там нет. Запустите `patch-zoo.cmd` снова — он выберет самую
свежую версию. Папки прежних версий со своими `extension.js.orig` можно удалить.

## Безопасность и границы

- Тело запроса и тело ответа прокси передаёт **без изменений** (байт-в-байт): он только
  переподписывает заголовки. Никакой подмены полей, моделей и сообщений нет — текст
  ошибки в Zoo приходит от шлюза, а не формируется прокси.
- Патчер меняет в бандле Zoo ровно две вещи: подключение `oc-sign.cjs` и аргумент
  `fetch` в конструкторе OpenAI-клиента. Тело запроса/ответа он не касается —
  подпись добавляет заголовки уже при отправке.
- Прокси слушает **только 127.0.0.1** — с других машин к нему не подключиться.
  Патчер сетевых слушателей не создаёт вообще.
- API-ключ в Roo — просто пароль для локального эндпойнта, реальная авторизация
  идёт устройственным ключом OpenCoder из `%LOCALAPPDATA%\OpenCoder\cc-web-credentials.json`.
  В Zoo (вариант с патчем) поле API Key вообще не используется для авторизации.
- Приватный ключ подписи не копируется и не передаётся: `oc-sign.cjs` читает
  `cc-web-credentials.json` из профиля пользователя при каждом запросе, тем же
  способом, что и `gw-proxy.mjs`.
- Все запросы Roo/Zoo уедут в шлюз **от вашего managed-устройства OpenCoder** — лимиты
  и учёт общие с вашим OpenCoder-клиентом. Если у администратора шлюза есть
  политика про сторонние клиенты — согласуйте; правильное стационарное решение —
  статический API-ключ от него.
